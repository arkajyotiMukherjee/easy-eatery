# Staff handoff and permitted pickup notifications

PostgreSQL Cloud mode applies migration 008 alongside the delivery/status migrations. The queue records verified provider timestamps without allowing replay or receipt time to refresh them. Both reply sends and proactive notifications reserve the transport timeout within the 24-hour customer-service window. Missing, future or expired timestamps fail closed. Console simulation does not send real messages; synchronous memory Cloud callbacks also refuse freeform sends without a valid provider window.

Help, allergy questions, payment problems and unsupported requests create idempotent branch-scoped staff handoffs. Their bilingual reply preserves the cart and makes no allergen-safety or response-time promise. Unsupported media routes to help without interpreting attachments. The staff panel shows only redacted request IDs/reasons. Owners/operators may explicitly record review without contact; viewers can read. Review is audited and never claims that a customer was contacted or that the issue was resolved.

For orders bound to a verified WhatsApp conversation, persisted domain transitions stage one notification per order/kind: restaurant accepted, ready, or staff recorded payment at pickup. Local pay-at-pickup acceptance and readiness remain unpaid. Sandbox acceptance is explicitly labeled as a test. Notifications contain no card data, checkout capability, amount, marketing copy or settlement claim. Old acceptance/readiness is suppressed if the order has advanced; uncertain/reversed sandbox payments suppress pending kitchen notifications.

The worker claims before sending, checks the current state and service window again, and runs network I/O outside transactions. Explicit provider rejections have bounded retries; ambiguous sends and expired claims park for review. Missing/expired windows route to `staff_required`. There is no unapproved utility-template fallback. Provider acceptance is separate from the signed receipt evidence described in `whatsapp-delivery-status.md`.

`GET /api/whatsapp/support` returns up to 100 scoped open handoffs and recent notification diagnostics. `POST /api/whatsapp/support/:id/review` requires `{"confirmation":"reviewed_without_contact"}` and current owner/operator authorization. A repeated or foreign review returns 409; successful review returns `customerContacted: false`. Use the restaurant's approved private support process for actual follow-up. Notification diagnostics have no resend control for uncertain outcomes.

The integration suite uses synthetic timestamps, fake transports and isolated PostgreSQL schemas to verify bilingual content, deduplication, restart/races, privacy, state supersession, window expiry/replay, bounded rejection retries and staff authorization. No real customer or provider acceptance is established. Approved sender/recipient access, real-device rehearsal, template approvals, retention periods, deletion/export policy and restaurant support ownership remain external gates. This feature does not choose a production retention period or purge audit/customer data.
